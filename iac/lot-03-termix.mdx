## Objectif

Ce lot donne à [Termix](/services/termix) un accès SSH contrôlé aux hôtes du homelab, par un compte dédié `termix-usr`. Ce compte n'est utilisable que par Termix, et chacune de ses actions privilégiées est tracée dans Loki. Le même lot permet de révoquer cet accès sur tout le parc en une commande.

| Élément | Valeur |
|---|---|
| **Outil** | Ansible — playbook `ansible/playbooks/termix-access.yml`, rôle `ansible/roles/termix_access/` |
| **Cible** | Groupe `[termix_hosts]` |
| **Commandes** | `make termix-check`, `make termix-apply`, `make termix-revoke` |

<Info>
  Le modèle a été validé le 19/10/2026 sur l'hôte pilote IMS-PBS (LXC 103) : connexion, sudo sans mot de passe, refus de la clé hors VM 104, traçabilité locale et dans Loki.
</Info>

---

## Principe de sécurité

L'accès repose sur trois verrous successifs :

| Verrou | Mécanisme | Ce qu'il empêche |
|---|---|---|
| **Accès à Termix** | `vpn-only` + OIDC Authentik (groupe `admins`) | Personne hors Tailnet ou hors groupe `admins` n'ouvre Termix |
| **Clé restreinte** | `from="192.168.1.52"` dans `authorized_keys` | Une clé volée est inutilisable depuis une autre machine que la VM 104 |
| **Connexion par clé uniquement** | Bloc `Match User termix-usr` dans `sshd` | Aucune attaque par mot de passe sur ce compte |

Le compte dispose d'un sudo sans mot de passe. Ce choix est assumé : un mot de passe sudo serait de toute façon stocké dans Termix pour le remplissage automatique, et ne protégerait donc pas contre une compromission de Termix.

### Traçabilité

- Chaque commande sudo est journalisée (`log_subcmds`) avec l'utilisateur d'origine, le TTY et la commande complète.
- Alloy envoie ces lignes vers Loki au moment où elles sont écrites. `termix-usr` étant root via sudo, il pourrait effacer le journal local : la copie dans Loki fait foi.
- Les sessions SSH sont aussi enregistrées par Termix (plugin Session Recording, rétention 30 jours).

```logql
{job="systemd-journal"} |= "termix-usr" |= "COMMAND=" != "pvesh"
```

Le filtre `!= "pvesh"` écarte les relevés automatiques du plugin Proxmox, qui exécute `sudo -n pvesh` à chaque synchronisation.

## Ce que fait le rôle

| État | Actions |
|---|---|
| `present` (défaut) | Installe sudo si absent · crée `termix-usr` (mot de passe verrouillé) · groupes `adm`, `docker` s'il existe, groupes spécifiques à l'hôte · clé restreinte · sudoers NOPASSWD journalisé · bloc sshd par clé uniquement |
| `absent` | Supprime le compte et son dossier personnel, le sudoers et le bloc sshd |

| Fichier géré sur l'hôte | Contrôle |
|---|---|
| `/home/termix-usr/.ssh/authorized_keys` | Exclusif : toute autre clé est retirée |
| `/etc/sudoers.d/termix-usr` | `visudo -cf` avant écriture |
| `/etc/ssh/sshd_config.d/50-termix.conf` | `sshd -t` après écriture |

---

## Variables

| Variable | Où | Rôle |
|---|---|---|
| `termix_access_pubkey` | `ansible/group_vars/all.yml` | Clé publique de la credential Termix — obligatoire, le rôle échoue sinon |
| `termix_access_source_ip` | `ansible/group_vars/all.yml` | `192.168.1.52`, IP source de Termix |
| `termix_access_extra_groups` | `ansible/inventory.ini`, par hôte | Groupes supplémentaires (ex. propriétaire des données sur le NAS) |
| `termix_access_docker` | Défaut du rôle | `true` : ajout au groupe docker s'il existe |

## Raccorder un hôte

<Steps>
  <Step title="Vérifier l'accès Ansible">
    L'hôte figure dans `[termix_hosts]` et `make ping HOST=<hôte>` répond `root`. Pour un LXC, applique d'abord le [lot 02](/iac/lot-02-acces-admin).
  </Step>

  <Step title="Simuler">
    ```bash
    make termix-check HOST=<hôte>
    ```
    Relis le diff : seuls le compte, la clé, le sudoers et le bloc sshd doivent apparaître.
  </Step>

  <Step title="Appliquer">
    ```bash
    make termix-apply HOST=<hôte>
    ```
  </Step>

  <Step title="Déclarer l'hôte dans Termix">
    Dans Termix, ouvre **Manage** → **Hosts** et ajoute l'hôte :
    - **Address** : l'IP **LAN** de l'hôte, port `22`
    - **Credential** : `termix-usr`
    - **Session Recording** : activé
    - **Docker** : activé uniquement sur IMS-Coolify et le worker

    <Warning>
      Termix doit joindre l'hôte **par le LAN**. La clé n'accepte que l'IP source `192.168.1.52` : une adresse Tailscale (`100.64.x.x`) serait refusée.
    </Warning>
  </Step>

  <Step title="Valider">
    Dans un terminal Termix sur l'hôte, `sudo -n whoami` doit répondre `root`. Vérifie ensuite dans Grafana que la commande apparaît dans Loki.
  </Step>
</Steps>

Pour raccorder tout le parc d'un coup : `make termix-check`, puis `make termix-apply`.

## Révoquer l'accès (urgence)

En cas de suspicion de compromission de Termix, coupe l'accès sur tout le parc :

```bash
make termix-revoke CONFIRM=oui
```

Sur un seul hôte, ajoute `HOST=<hôte>`. Ensuite :
1. Supprime la credential `termix-usr` dans Termix.
2. Supprime l'entrée « Termix — clé SSH termix-usr » dans Vaultwarden.
3. Examine l'activité récente dans Loki et dans les enregistrements de sessions Termix.

---

## Rotation de la clé

1. Dans Termix : **Manage** → **Credentials** → **termix-usr** → **Generate Ed25519** → enregistre.
2. Dans Vaultwarden : remplace la clé privée.
3. Dans `ansible/group_vars/all.yml` : remplace `termix_access_pubkey`.
4. Lance `make termix-apply`. L'ancienne clé est retirée automatiquement.

Si l'IP de la VM 104 change, modifie `termix_access_source_ip`, puis relance `make termix-apply`.

---

## Vérification manuelle sur un hôte

```bash
id termix-usr
sudo cat /home/termix-usr/.ssh/authorized_keys
sudo visudo -cf /etc/sudoers.d/termix-usr
sudo sshd -T -C user=termix-usr,host=x,addr=192.168.1.52 | grep -iE 'passwordauth|authenticationmethods'
sudo journalctl -t sudo --since -1h | grep termix-usr
```

Attendus :
- `termix-usr` appartient au groupe `adm` (et `docker` s'il existe).
- La clé commence par `from="192.168.1.52"`.
- Le sudoers affiche `parsed OK`.
- `sshd` renvoie `passwordauthentication no` et `authenticationmethods publickey`.

## Dépannage

| Symptôme | Cause | Correction |
|---|---|---|
| `Missing privilege separation directory: /run/sshd` | `sshd` lancé par `ssh.socket` (LXC Debian) | Géré par le rôle. Aucun rechargement n'est nécessaire : la config est relue à chaque connexion |
| `ssh.service en failed` avec `ssh.socket` actif | Conflit de port historique, sans impact | `sudo systemctl reset-failed ssh.service` |
| Termix : `Permission denied (publickey)` | Hôte joint hors LAN, ou clé non à jour | Vérifie l'adresse dans Termix et `termix_access_pubkey` |
| Refus malgré une clé correcte | `AllowUsers` / `AllowGroups` dans `sshd` | `sudo sshd -T | grep -iE 'allowusers|allowgroups'`, puis ajoute `termix-usr` |
| Bruit `pvesh` dans Loki | Synchronisation du plugin Proxmox | Filtre `!= "pvesh"`, intervalle des stats ≥ 60 s |
